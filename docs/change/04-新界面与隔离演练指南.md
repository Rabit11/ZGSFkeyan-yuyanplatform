# 项目变更新界面与隔离演练指南

当前扩展以 [多项变更与多轮修订](08-多项变更与多轮修订.md) 为准：已支持一单多项、保存版本及 9 个演练场景。下文单字段说明为此前实现记录。

本轮在原“实施阶段 → 项目变更”路由内继续改造。原平台顶栏、侧栏、路由配置、其他业务组件和业务接口没有修改。新增样式由 Change.vue 路由组件加载，限定在模块根节点、组件作用域及 `.change-drawer` 弹层中。

## 入口与启动

| 环境 | 页面 | 数据库 / 会话 / 附件 |
| --- | --- | --- |
| 原本地平台 | http://127.0.0.1:6006/#/implement/change | rpm / Redis DB 0 / rpm-attachments |
| 项目变更测试模式 | 原平台“项目变更”页面内点击“进入测试模式” | rpm_change_lab / Redis DB 1 / rpm-change-lab |

原页面右上方“进入测试模式”在当前页面建立独立演练会话，默认登录演练负责人 100012，不再跳转 6026 或回到平台首页。浏览器请求通过当前地址的 `/api/changes/lab/` 进入原后端，再由原后端连接内部演练服务；原平台 token 保留在 localStorage，模块演练 token 独立保存在 sessionStorage。切换演练身份不会更换原平台身份，点击“退出测试模式”恢复原平台列表。6026 仅保留为服务器本机诊断入口，远程用户不需开放或访问该端口。测试环境有黄色 TEST 标识；“使用场景与操作脚本”展开 8 个场景，每个场景包含目标、岗位顺序、具体步骤及验收结果。

实际源码目录为 `/home/dev/projects/ZGSFkeyan-yuyanplatform`，在该目录执行：

```bash
python3 scripts/local-platform.py start
python3 scripts/change-lab.py start
python3 scripts/change-lab.py status
```

`change-lab.py start` 重复执行会保留现有演练数据。首次从仓库 SQL 初始化专用数据库，不复制本地平台业务数据；自动创建 `LAB_CHANGE_S01` 至 `LAB_CHANGE_S08` 八个演练项目。测试后这八个项目保留供人工使用。

```bash
# 重置八个演练场景及其申请、附件；仅作用于专用演练项目
python3 scripts/change-lab.py reset-scenarios
# 仅重启演练前后端，不停止共享 MySQL、Redis、MinIO
python3 scripts/change-lab.py restart
python3 scripts/change-lab.py stop
```

服务仅监听 127.0.0.1。测试模式复用基础设施进程，但数据库用户只获专用库权限、JWT 密钥不同、Redis 会话库不同、附件 bucket 不同。MinIO 服务账号仍共用，因此属于本地业务数据隔离，不是独立租户或恶意代码安全沙箱。实际演练按正常登录和审批接口执行，没有跳过权限的“自动通过”。项目变更请求强制使用真实网络接口，不接入全局可选 mock 适配器；连接异常会提示错误，不产生模拟成功。测试标识由后端配置返回，修改 URL 的 `testMode` 参数不能开启测试身份控件。

## 界面依据与变化

参考达索官方 [ENOVIA 工程变更管理](https://www.3ds.com/products/enovia/engineering-change-management) 的对象、影响、责任及审批追溯组织方式，以及 [ENOVIA Change Manager](https://3dswym.3dexperience.3ds.com/wiki/3dexperience-platform-user-s-community/enovia-change-manager_nEs7um-fQu21eDTeUWziUA) 的变更对象与任务入口。界面为本项目的适配设计，不是达索产品的像素级复制或品牌页面。

- 深蓝应用标题区、青蓝操作色、浅灰工作区、紧凑工具栏、低圆角表格，形成工程工作台层次。
- 申请面板显示对象图标、申请编号、标题、关联项目和状态；内部导航定位属性内容、材料、履历。
- 宽屏右侧固定展示当前任务、实际办理人、提交准备清单和生效规则；窄屏移至内容前，页底操作保留。
- 事项类别可缩小对象选择范围；项目变更与数据纠错有用途说明；材料建议按经费、周期、外协、指标等事项显示。
- 移除把并发控制计数显示为业务 REV 的做法；已保存状态使用普通文字，后台 revision 继续用于防止重复操作。
- 去掉本页面泛化的职责条，替换为依据实际申请权限的任务指引；不修改共用职责条组件。
- 路由跳转和浏览器刷新提示未保存内容。提示取消时保留当前编辑；确认放弃后不会恢复未保存内容。

## 人员、提交与权限

测试账号密码均与工号相同，先用 `100012 / 100012` 登录，在测试页面选择演练身份。

| 工号 | 用途 |
| --- | --- |
| 100012 | 项目负责人，发起及确认技术负责人草稿 |
| 100014 | 技术负责人，准备草稿和附件，不直接提交 |
| 100005 | 单位主管，普通初审或渠道规定的终审/确认 |
| 100006 | 单位科技主管，CLM/BOKH 初审 |
| 100004 | 总部科技主管，项目变更总部审核、数据变更确认 |
| 100009 | 演练法务；仅在隔离环境获得配置授权，不能据此认定正式资质 |
| 100001 | 管理员，本模块业务只读 |

本轮法务候选人从“任意在岗人员”收紧为 `RPM_CHANGE_LEGAL_EMPLOYEES` 中的工号，且必须在岗、非管理员/领导、非申请人。该配置只影响项目变更模块。正式名单默认空；未确认实际人员之前不预设其法律职责。

正式环境可设置经业务确认的逗号分隔工号后重启后端；启动脚本继承此环境变量。例如将变量设为经确认的工号列表，再重启后端。不要把测试环境的 `100009` 直接当作正式配置。

重大变更可不选法务保存草稿；提交时必须具备法务及全流程各节点的有效办理人。页面显示缺失原因，服务端也独立校验，不能绕过按钮直接提交。其他必填内容目前仍须完整才能保存草稿。

技术负责人创建的草稿进入本项目负责人的“待我办理”；创建人负责补正，负责人核对后提交。提交前至少一份 SUPPORT 材料；MJKY 归档另需 EXTERNAL 材料及回执号。

## 场景、脚本与测试用例

场景唯一来源：[`scenarios.json`](../../frontend/src/views/implement/change/scenarios.json)。测试页面直接读取该文件；每条都列出目标、步骤、预期结果与自动化脚本，不另维护互相矛盾的场景副本。

| 场景 | 目标 | 自动化覆盖 |
| --- | --- | --- |
| S01 里程碑延期 | 单位、总部通过后才回写单个目标 | API 字段/路由；浏览器基本流程；Lab 预填 |
| S02 经费法务 | 单位→指定法务→总部，不合格人员不可代办 | API 重大变更；浏览器法务；Lab 名单/缺配 |
| S03 驳回补正 | 驳回不回写，补正重提保留全部意见 | API 驳回重提；浏览器完整操作 |
| S04 名称纠错 | 数据变更由总部科技主管确认 | API 数据路由/岗位；浏览器数据页面 |
| S05 民机线下归档 | 总部通过后等待材料及回执，归档才生效 | API 与浏览器实际上传/归档 |
| S06 技术负责人交接 | 创建与提交分工，负责人能找到草稿 | API 权限；浏览器技术草稿；Lab 待办 |
| S07 上海创新 | 一般项目变更单位终审直接办结 | API 渠道路由及写回 |
| S08 CLM 两级办理 | 单位科技主管初审、单位主管确认 | API CLM/BOKH 岗位与状态 |

人工演练顺序：展开场景 → 查看目标和办理顺序 → 选发起身份 → “开始此场景”预填 → 人工核对并保存 → 上传真实演练文件 → 提交 → 关闭面板切换下一岗位 → “待我办理”审核 → 回到申请核验状态及履历。身份切换是一次正常登录；不会自动保存草稿或填写审核结论。

“开始此场景”只预填，不自动上传、不自动提交，也不会把人工场景标记为已通过。同一个场景办结后若需再次调整相同字段，请先重置演练场景，或填写另一个有效的新值。

运行整套模块验证：

```bash
python3 qa/change/run-lab.py
```

脚本先确认测试服务运行，固定 API 为 6026、SQL 为 rpm_change_lab。QA 夹具使用随机 `QA_CHANGE_...` 项目，结束后只清理本次夹具及精确附件对象；不清理供用户操作的八个场景。可执行文件/浏览器依赖沿用本地部署环境。

新增 `lab.mjs` 覆盖：后端环境标识、跨环境令牌拒绝、法务名单、后续岗位缺失、技术交接待办、场景预填、刷新取消、站内离开取消、离开后的 CSS 一致性、演练身份切换、窄屏操作可见、正式页面无法伪造测试模式。

## 仍需明确的边界

当前仍按单个字段申请，未扩展多字段事务变更、完整外协合同或结构化指标体系；历史申请保留只读，未自动补建关联信息。需求未明确的渠道路径仍沿用上一轮默认口径，详见需求整理中的假设；全平台其他入口写入限制没有改动。上述边界不因为测试通过而视为业务验收完成。

新风格的人工视觉认可、真实法务名单、未知渠道规则仍需业务确认。自动化报告证明列出的操作与结果，不等于这些待确认项已经解决。

入口修复与从原平台按钮开始的真实写入证据，见 [入口修复验证](06-测试入口修复与真实接口验证.md)。

当前单地址隧道接入方式见 [单地址隧道入口验证](07-单地址隧道入口验证.md)，浏览器不依赖任何独立测试端口。
