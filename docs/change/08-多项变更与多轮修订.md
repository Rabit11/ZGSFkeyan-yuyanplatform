# 多项变更、多轮修订与周转方

当前页面交互已按用户明确需求更新为 [多类别多对象直接填写](09-多类别多对象直接填写.md)，下文逐项加入的操作说明为此前版本记录。

本轮在原“项目变更”页面内扩展，浏览器继续使用原平台及隧道地址。测试模式沿用同源 `/api/changes/lab/...`，没有新增浏览器端口。原外层导航和其他业务页面不变。

## 本轮口径

“一次进行多轮修改”落实为：同一份申请可以加入多个变更项；草稿及退回补正期间可反复增删、编辑、保存，每次保存形成独立内容版本；整份申请统一提交、统一审批、统一生效。审批进行中不开放追加内容，避免已经审核的内容被替换；退回后可继续修订，重新提交从首节点开始。

每份申请关联一个实施中项目，包含 1–50 个字段。同一字段只能出现一次，可编辑已选项。项目业务调整与数据纠错分别申请，保持 V19.1 两类审批口径。经费、周期、外协任一项出现，即按重大变更增加法务节点，不受排列顺序影响。

## 用户操作

1. 发起变更，选择项目和类型。类型说明分别给出业务调整与登记纠错的范围；选定内容后锁定类型，避免误切换清空清单。
2. 可按事项类别缩小范围，查看各类别可选对象数量。对象选项带有类别、业务对象、字段；已经加入的对象显示“✓ 已选”。筛选不会删除已选内容。
3. 填写调整后内容，点击“加入已选项”。下方清单展示数量、类别、对象、前后值及法务标记；点击“编辑此项”后用“更新已选项”确认，或移除不需要的项。
4. 继续选择另一对象。尚未确认的编辑会阻止切换并提示处理；“取消当前编辑”会保留已加入清单的内容。直接保存草稿也会自动收录正在编辑的有效项。
5. 填写整份申请的标题、共同缘由，涉及重大项时选择法务。保存后生成第 1 版，再次保存形成第 2、3……版。材料区按清单所含类别提供联合材料建议。
6. 上传材料，核对已保存路径及所有办理人。右侧展示“提交后交给”；技术负责人草稿还显示负责确认提交的项目负责人。
7. 审批人打开详情时可查看全部前后值、历史版本和材料。右侧及审核确认框说明“通过后交给”与“退回给”。同一节点存在多个合格办理人时，标明任一办理。
8. 被退回后由发起人补正、保存、重新提交；旧版本和驳回意见保留。终审或必须的线下归档完成后，全部变更项在同一事务中生效。

“修改版本”位于办理履历区，每版可展开查阅当时的标题、缘由和完整清单。内容保存版本与后台并发控制 `revision` 不同，上传附件、审批不会增加内容版本号。版本为历史快照，目前提供查阅，不提供一键恢复或自动逐字差异比较。

## 后端和兼容

新增 `migration_change_v3.sql`，仅增加两个项目变更表：

| 表 | 用途 |
| --- | --- |
| `proj_change_item` | 当前申请的所有变更项，按申请和字段设置唯一约束 |
| `proj_change_round` | 每次保存的完整 JSON 快照、版本号、保存人和时间 |

保存接口增加 `items: [{targetKey, targetId, category, afterValue}]`，由服务端读取原值、检查字段白名单、所属项目、类型类别、重复项、数量及业务约束。旧版单字段请求仍支持；旧受控记录没有清单时按原字段读取，首次编辑前保留一份旧内容快照。旧记录的首次快照时间为本次接入留档时间，不追溯推断过去的修改时间。没有受控对象关联的历史申请仍只读。

原 `proj_change` 标量前后值及 control 对象字段保留首项摘要兼容旧看板；新的 `items` 是完整内容，`categories` 和 `itemCount` 用于列表展示。`route` 在详情中带各节点 `handlers`，并返回 `nextNode`、`nextHandlers`、`returnTo` 和技术负责人交接使用的 `submitHandlers`。

提交和生效前锁定项目、核验全部目标原值与业务状态。周期及节点日期按整份申请的拟生效状态联合校验，因此可在同一申请延长项目周期和交付日期，也可一并收拢付款、交付日期后缩短周期。未选节点仍构成约束。任一项冲突或不合法，会使整个事务失败，审批状态、回写标记和其他项均不提交。项目渠道改变导致原审批路径失效时要求退回重新保存。

保存内容、替换清单、增加版本和履历均在同一事务内；沿用原 revision 冲突检查和请求幂等控制。审批期间不可编辑或删改支撑材料。删除草稿保留审计及版本快照，清除当前项引用。

本地启动脚本会为正式库和独立演练库各自执行幂等增量建表，不复制、不重置业务数据。正式库现有受控记录按读取兼容处理。

## 演练和测试

面板新增 S09“多项变更 · 多轮修订与周转”，用 `LAB_CHANGE_S09` 独立项目演练两项联合变更、多次保存、退回、法务及终审。操作脚本和目标直接展示在原页面测试模式中。

另保留了可直接查阅的真实演练样例：在测试模式搜索“多项样例”，可查看 `LAB_PROOF_BATCH_V3` 项目的两项变更、三个保存版本、一次退回以及单位→法务→总部的审批记录。样例使用独立演练库及真实附件，正式数据不受影响；`qa/change/seed-batch-proof.mjs` 可幂等准备此样例。

自动化脚本：

| 脚本 | 重点 |
| --- | --- |
| `qa/change/batch.mjs` | 12 组真实数据库/API 场景：多项版本、幂等、重复及混合类型、跨项目、重大法务、周期联动、冲突、退回、数据纠错、归档及旧版兼容 |
| `qa/change/batch-browser.mjs` | 从原端口进入演练，实际添加/编辑/移除清单、展开版本、上传文件、退回重提、三角色审批、窄屏布局 |
| `qa/change/workbench.test.mjs` | 保留原 8 项，加 5 项清单保留、防覆盖、全量提交、草稿/详情隔离和渠道名称显示测试 |
| `qa/change/selection-labels.mjs` | 实际打开 S09 脚本；保存前核对渠道名称显示及版本导航 |
| `qa/change/api.mjs` | 原有 57 组单项业务和权限回归 |
| `qa/change/browser.mjs` | 原有页面操作回归 |
| `qa/change/lab.mjs` | 9 场景入口、身份隔离、样式与离开页面保护 |
| `qa/change/tunnel-api.mjs`、`entry.mjs` | 同源真实 API 转发与完整文件、审批链路 |

执行入口为 `python3 qa/change/run-lab.py`，先完成前后端构建并重启相应后端，使验证针对最新构建。单独运行新增测试时设 `CHANGE_QA_DB=rpm_change_lab CHANGE_QA_BASE=http://127.0.0.1:6026`；这是本机测试脚本的服务选择，浏览器端到端脚本仍通过原 `6006` 入口进入隔离模式，并阻止浏览器连接 `6026`，用户隧道不需要该端口。

本轮实际输出位于 `deploy/change-batch/`，包括构建日志、接口结果、浏览器结果和截图。最终验证汇总另见同目录 `verification.json`。

## 本轮实际验证结果（2026-09-14）

前端类型检查和构建成功，两个运行中的后端均已核对为当前构建。以下套件全部通过：新增真实接口 12 组、新增浏览器流程 6 组、最终场景与选择标签 2 组；既有接口 57 组、既有浏览器操作 20 组；演练检查 13 组、同源转发 5 组、单地址完整流程 5 组；其他业务页面只读检查 11 项；前端单元测试 22 项、后端单元测试 43 项。

检查了 378 个已有文件的范围快照，未发现约定范围外的改动，三份原始 Office 资料的哈希未变。单地址流程验证中正式业务记录未改变。用户实际隧道 URL 尚未提供，本次覆盖原入口及单地址 HTTPS 模拟，不宣称已直连验通用户实际隧道。

保留样例：项目 `LAB_PROOF_BATCH_V3`，申请 ID `166`，状态已办结，2 个变更项、3 个内容版本。可在测试模式搜索“多项样例”核验实际数据与办理履历。
