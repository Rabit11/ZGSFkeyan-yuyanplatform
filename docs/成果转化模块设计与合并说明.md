# 成果转化模块设计与合并说明

## 模块目标

成果转化模块承接验收阶段的已交付交付物，以成果包作为最小管理单元，覆盖向型号转化和向市场转化两条路径。成果编号由服务端生成并与交付物双向绑定，支持从项目台账追踪成果包，也支持从成果包反查成果构成。

## 业务规则

- 一个成果包必须属于一个项目，并至少绑定一项该项目内状态为已交付的交付物。
- 一项交付物只能属于一个成果包；绑定、解绑和成果编号回写在同一事务内执行。
- 转化方式、转化形式和转化进度使用总部维护的数据字典；转化形式按转化方式级联。
- 完成转化必须填写实际转化时间并上传至少一份成效佐证，实际时间不能晚于当天。
- 转化进度与审核状态独立。填报“已完成”在总部备案前不会进入项目台账和看板的完成统计。
- 审批流为项目团队填报或更新、二级单位管理团队审核确认、总部管理团队备案。二级单位可退回，总部只备案。
- 已备案成果需要更新进展时发起新一轮填报，上一轮内容随办理履历保留。

## 状态模型

审核状态依次为 `DRAFT`、`UNIT_REVIEW`、`HQ_RECORD`、`RECORDED`；审核退回进入 `RETURNED`。提交、审核、退回、备案及再次更新均记录操作人、时间、意见和当次业务快照。

业务进度沿用 `NOT_STARTED`、`NEGOTIATING`、`SIGNED`、`DONE`。`reported_status` 和 `reported_actual_date` 保存本轮填报值，只有备案完成后才同步为平台聚合使用的 `status` 和 `actual_date`。

## 接口与权限

- `GET /api/transforms`：按当前用户数据范围分页查询，支持项目、进度、审核状态、方式、单位和关键词筛选。
- `GET /api/transforms/{id}`：读取成果构成、材料、履历和当前用户可办动作。
- `POST /api/transforms`、`PUT /api/transforms/{id}`：项目负责人或联系人填报；所属项目和成果编号不可由客户端覆盖。
- `POST /api/transforms/{id}/workflow`：项目负责人提交，二级单位负责人审核，总部处室备案。
- 修改和办理必须携带 `revision`，版本不一致返回 409，避免多人编辑相互覆盖。

## 部署和合并

新建数据库直接使用 `schema.sql`。已有数据库在发布后端前执行 `migration_transform_v1.sql`；脚本逐字段判断并可重复运行。迁移会把历史完成状态保存为待核对的填报状态，待走完审核备案后再纳入全局完成统计。

前端变更集中在成果转化页面、独立工具函数和 Mock 适配。后端变更集中在成果转化控制器、实体和独立迁移脚本。没有修改其他模块的路由或公共视觉样式，便于与主分支并行合并。
